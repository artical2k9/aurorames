## ERR-MES-059 — Angular subscribe callbacks mutating template-bound properties trigger NG0100 across entire app
**Date:** 2026-06-05  **Category:** Frontend — Angular Change Detection  **Status:** Promoted 2026-06-05
**Symptom:** `RuntimeError: NG0100: ExpressionChangedAfterItHasBeenCheckedError` thrown in dev mode on page load and on form-save errors. Affected 14 components across BOM, ECO, Item Master, UDF, and shared features. The error surfaced incrementally — fixing one component revealed the same pattern in others, requiring 4 separate fix passes.
**Root cause:** Angular dev mode runs change detection twice (a render pass then a `checkNoChanges` pass). When an HTTP Observable emits inside the Angular zone (e.g. from `ngOnInit`, `constructor`, `ngAfterViewInit`, or a form-submit callback), it mutates template-bound properties (`loading`, `items`, `serverError`, `parentItem`, etc.) between the two passes. Angular's second pass detects the discrepancy and throws. The pattern is latent in every component that subscribes to HTTP and mutates state in the callback; it surfaces only when a response arrives synchronously-enough to land within the same CD cycle.
**Fix applied:** Injected `ChangeDetectorRef` into all 14 affected components and called `this.cdr.detectChanges()` at the end of every `next:` and `error:` callback that mutates any template-bound property. Full component list documented in ERR-MES-059 archive entry.
**Rule:** Every Angular component that has a `.subscribe()` call mutating a template-bound property MUST inject `ChangeDetectorRef` and call `this.cdr.detectChanges()` at the end of both the `next:` and `error:` callbacks. This applies to page-load subscribes (`ngOnInit`, `constructor`), user-action subscribes (`save()`, `delete()`, `obsolete()`), and shared/child components. When creating any new component with an HTTP subscribe, add `cdr` injection and `detectChanges()` as a mandatory part of the component template. See CLAUDE.md §Angular Change Detection Rules.

## ERR-MES-060 — Keycloak 25 stopped auto-including `sub` in access tokens; jwt.getSubject() returns null
**Date:** 2026-06-05  **Category:** Backend — Keycloak / JWT  **Status:** Promoted 2026-06-05
**Symptom:** `POST /api/v1/ecos` returned 409 with `null value in column "initiated_by" violates not-null constraint`. `created_by` on the same row was `"system"`. Multiple services also at risk: `platform.user_grid_preferences.user_id NOT NULL`, `Optional.of(auth.getName())` NPE path in iam-service/platform-service JpaConfig, null actor in Envers revinfo.
**Root cause:** Keycloak 25 changed behaviour — `sub` is no longer automatically included in access tokens unless an explicit `oidc-usermodel-property-mapper` (user.attribute=id, claim.name=sub) is added to the client or client scope. Code that passed null directly into NOT NULL columns caused 409; code that called `Optional.of(null)` would NPE with 500.
**Fix applied:** (1) Added `sub` protocol mapper to `mes-frontend` client via Keycloak admin API — takes effect immediately without restart. (2) Persisted the mapper to `keycloak/mes-realm.json` so it survives future realm reimports. (3) Hardened `JwtClaimsExtractor.nullSafeSubject()` in lib-common-security with `sub → preferred_username → "unknown"` fallback chain. (4) Hardened `MesRevisionListener.resolveUserId()` in lib-common-audit with same fallback. (5) Fixed `Optional.of(auth.getName())` NPE in iam-service and platform-service JpaConfig. (6) Added `subjectOf(Jwt)` null-safe helper to work-order-service EcoController.
**Rule:** Every Keycloak client must include an explicit `sub` mapper. Never call `jwt.getSubject()` without a null fallback chain. See CLAUDE.md §Keycloak Protocol Mapper Rules.

## ERR-MES-063 — Missing producer serializer config; KafkaTemplate cannot serialize Map payloads
**Date:** 2026-06-05  **Category:** Backend — Kafka  **Status:** Promoted 2026-06-05

## ERR-MES-023 — Hibernate Envers rejects audited relation to non-audited entity
**Date:** 2026-05-21  **Category:** Backend — Hibernate Envers  **Status:** Open
**Symptom:** All integration tests that load the Spring ApplicationContext failed with `EnversMappingException: An audited relation from com.mikemes.iam.domain.RolePrivilegeAssignment.privilege to a not audited entity com.mikemes.iam.domain.Privilege! ## ERR-MES-024 — KC admin calls made without response-code assertion; mapper registration failed silently
**Date:** 2026-05-21  **Category:** Testing — Keycloak  **Status:** Open
**Symptom:** IT tests returned 401 UNAUTHORIZED for 9+ CI runs after switching to `oidc-hardcoded-claim-mapper`. `org_id` was never injected into any JWT. No error appeared in test output or Spring logs.
**Root cause:** `Response r2 = kcAdmin.realm(...).clients().get(clientUuid).getProtocolMappers().createMapper(orgMapper); r2.close();` — `r2.getStatus()` was never called. KC25 returned a non-201 response (mapper registration failed silently). `r2.close()` released the connection without surfacing the error. The test proceeded as if the mapper existed. KC never injected `org_id`. `MissingClaimException` fired on every authenticated request.
**Fix applied:** Abandoned KC-based JWT issuance for IT tests entirely. Replaced with locally-signed RSA JWTs (`RSAKeyGenerator` + `SignedJWT` + `RSASSASigner`) and a `@TestConfiguration NimbusJwtDecoder` bean backed by the local RSA public key. `org_id` and `roles` are embedded directly at signing time — no KC dependency for JWT content.
**Rule:** (a) Every KC Admin API call that creates a resource (`clients().create()`, `getProtocolMappers().createMapper()`, `users().create()`) returns a JAX-RS `Response`. Always call `r.getStatus()` and assert `== 201` before calling `r.close()`. A silent non-201 means the resource was never created, but the test will not fail until runtime. (b) In IT tests, never rely on KC to issue JWTs — use locally-signed RSA JWTs. KC should only be used to test what KC actually does (user/role management operations). Token issuance via KC in tests adds a fragile KC-version-specific dependency that breaks silently. (c) When providing a test `JwtDecoder` via `@TestConfiguration` + `@Import`, always add `@Primary` to the `@Bean` method. `@ConditionalOnMissingBean(JwtDecoder.class)` on Spring Boot's auto-configured decoder has no guaranteed evaluation order relative to `@Import`-ed test beans in Spring Boot 3.5 — without `@Primary`, the wrong decoder may be used and all JWTs will be rejected with 401. (d) Never set `spring.security.oauth2.resourceserver.jwt.issuer-uri` to an empty string `""` to "suppress" auto-configuration — `@ConditionalOnProperty` treats empty string as present and Spring Boot will attempt to create a `SupplierJwtDecoder` regardless.

## ERR-MES-026 — LocalPrivilegeCache: lazy-loaded Privilege throws outside Hibernate session
**Date:** 2026-05-21  **Category:** Backend — JPA / Security  **Status:** Open
**Symptom:** All ADMIN-token IT tests returned 5xx (authentication/runtime failure) while VIEWER-token tests returned 403 as expected. Pattern: tests expecting 200/201/204/400/404 all failed; tests expecting 401 (no token) and 403 (VIEWER) all passed.
**Root cause:** `LocalPrivilegeCache.getPrivilegesForRole()` had no `@Transactional`. Spring Data JPA repository methods open and close their own transaction. After `findActiveByRoleId()` returned, the Hibernate session was closed. ## ERR-MES-046 — `@DynamicPropertySource` runs before `@RegisterExtension`; Keycloak `issuer-uri` always invalid → all business IT tests return 401
**Date:** 2026-05-26  **Category:** Testing — Spring Test / Keycloak Lifecycle  **Status:** Open
**Symptom:** After fixing V007 (commits `f03b924`, `3041505`, `18a23a0`), the Spring ApplicationContext loaded successfully, but ALL 26+ business IT tests failed. Tests that expected 201 CREATED NPE'd with `Cannot invoke "java.net.URI.getPath()" because "HttpHeaders.getLocation()" is null`. `postWithNoPrivilegesReturns403()` failed (expected 403, got 401). `getUnauthenticatedReturns401()` failed (assertion on response body failed, status was correct). The Spring Test framework evaluates `@DynamicPropertySource` static methods during context initialization, which happens BEFORE JUnit 5 `@RegisterExtension` extensions start their containers. At evaluation time, `KEYCLOAK.isRunning()` is always `false` and `getAuthServerUrl()` returns a placeholder or throws. The issuer-uri therefore pointed to an unreachable URL. Spring Security's JWT decoder validates the `iss` claim in incoming JWTs against this URL — mismatch → 401 for every authenticated request. The `@Primary` `NimbusJwtDecoder` overrides it, so no network call is made.
**Rule:** (a) Never use Keycloak to issue JWTs in `@SpringBootTest` integration tests. The `@RegisterExtension` Keycloak container starts AFTER `@DynamicPropertySource` evaluates — so `issuer-uri` will always be wrong. Use a locally-signed RSA JWT pair with `@Primary NimbusJwtDecoder`. (b) Use `jwk-set-uri` (not `issuer-uri`) in test properties; `issuer-uri` triggers OIDC discovery at startup which contacts a real server. (c) A `@Primary PrivilegeCache` with hardcoded role mappings avoids calling the IAM service from integration tests. This is a recognised promoted lesson — see ERR-MES-024 in the archive. The recurrence here (3 CI rounds, three different fix attempts) suggests the lesson was not applied early enough because the existing Keycloak IT infrastructure gave a false sense of correctness.
