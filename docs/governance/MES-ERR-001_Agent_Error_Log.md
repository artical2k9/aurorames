## ERR-MES-020 — `gradlew` missing execute bit breaks Linux CI
**Date:** 2026-05-21  **Category:** CI — Permissions  **Status:** Promoted 2026-05-22
**Symptom:** Both Java and SonarCloud CI jobs failed immediately with `Permission denied` (exit 126) on `./gradlew` on ubuntu-latest runner.
**Root cause:** `gradlew` was committed from Windows where the POSIX execute bit is not tracked by the filesystem. Git stored the file as mode `100644` instead of `100755`. Linux runners cannot execute it.
**Fix applied:** `git update-index --chmod=+x gradlew` — sets the execute bit in the Git index without changing file content. Committed and pushed; CI re-ran and passed.
**Rule:** After scaffolding or copying a Gradle project on Windows, always run `git update-index --chmod=+x gradlew` before pushing. Verify with `git ls-files --stage gradlew` — must show `100755`.

## ERR-MES-022 — Keycloak 25+ ROPC fails on new realms without `setDirectGrantFlow`
**Date:** 2026-05-21  **Category:** Testing — Keycloak  **Status:** Promoted 2026-05-22
**Symptom:** `KeycloakSupportTest.createUser_andFetchToken_returnsJwt()` failed with `NullPointerException: Cannot invoke "JsonNode.asText()" because the return value of "JsonNode.get(String)" is null`. All integration tests that use `fetchToken()` with ROPC fail the same way.
**Root cause:** Keycloak 25+ ships a new realm with the "direct grant" flow disabled by default. Creating a realm via the Admin API without calling `realm.setDirectGrantFlow("direct grant")` means the ROPC token endpoint returns `{"error":"access_denied"}` with no `access_token` field. `JsonNode.get("access_token")` returns null → NPE.
**Fix applied:** (1) Added `realm.setDirectGrantFlow("direct grant")` to realm creation. (2) Switched from `setCredentials()` in create body to `resetPassword(temporary=false)` after creation — this both sets the password and removes `UPDATE_PASSWORD` from required actions. (3) Added `email`, `emailVerified=true`, `firstName`, `lastName` to test users — Keycloak 26 (used by `dasniko/testcontainers-keycloak:3.4.0`) enables User Profile by default; users missing required profile fields get `UPDATE_PROFILE` as a required action, which blocks ROPC even after `resetPassword()`. (4) Added null-check in every `fetchToken()` with the raw response body in the exception message.
**Rule:** When creating test users for Keycloak 26+ ROPC: (a) `realm.setDirectGrantFlow("direct grant")` on realm create; (b) `user.setEmail/setEmailVerified(true)/setFirstName/setLastName` — User Profile is on by default in KC 26 and requires these fields; (c) call `resetPassword(cred)` with `temporary=false` after creating the user instead of embedding credentials in the create body; (d) null-check `access_token` in `fetchToken()` and include the raw Keycloak response in the error message for diagnostics.

## ERR-MES-023 — Hibernate Envers rejects audited relation to non-audited entity
**Date:** 2026-05-21  **Category:** Backend — Hibernate Envers  **Status:** Promoted 2026-05-22
**Symptom:** All integration tests that load the Spring ApplicationContext failed with `EnversMappingException: An audited relation from com.mikemes.iam.domain.RolePrivilegeAssignment.privilege to a not audited entity com.mikemes.iam.domain.Privilege! Such a mapping is possible but requires using @Audited(targetAuditMode = NOT_AUDITED).`
**Root cause:** `RolePrivilegeAssignment` is annotated `@Audited` at the class level. Hibernate Envers inherits this audit configuration to all `@ManyToOne` relations, including `privilege`. Because `Privilege` has no `@Audited` annotation, Envers rejects the mapping at startup, preventing the entire ApplicationContext from loading.
**Fix applied:** Added `@Audited(targetAuditMode = RelationTargetAuditMode.NOT_AUDITED)` to the `privilege` field in `RolePrivilegeAssignment`. This tells Envers to record only the FK reference (ID) in the audit table without requiring `Privilege` to be audited itself.
**Rule:** When a class is `@Audited` and has a `@ManyToOne` relation to an entity that is NOT `@Audited`, annotate that field with `@Audited(targetAuditMode = RelationTargetAuditMode.NOT_AUDITED)`. Without this, Envers fails at startup with `EnversMappingException` — not at query time.

## ERR-MES-024 — KC admin calls made without response-code assertion; mapper registration failed silently
**Date:** 2026-05-21  **Category:** Testing — Keycloak  **Status:** Promoted 2026-05-22
**Symptom:** IT tests returned 401 UNAUTHORIZED for 9+ CI runs after switching to `oidc-hardcoded-claim-mapper`. `org_id` was never injected into any JWT. No error appeared in test output or Spring logs.
**Root cause:** `Response r2 = kcAdmin.realm(...).clients().get(clientUuid).getProtocolMappers().createMapper(orgMapper); r2.close();` — `r2.getStatus()` was never called. KC25 returned a non-201 response (mapper registration failed silently). `r2.close()` released the connection without surfacing the error. The test proceeded as if the mapper existed. KC never injected `org_id`. `MissingClaimException` fired on every authenticated request.
**Fix applied:** Abandoned KC-based JWT issuance for IT tests entirely. Replaced with locally-signed RSA JWTs (`RSAKeyGenerator` + `SignedJWT` + `RSASSASigner`) and a `@TestConfiguration NimbusJwtDecoder` bean backed by the local RSA public key. `org_id` and `roles` are embedded directly at signing time — no KC dependency for JWT content.
**Rule:** (a) Every KC Admin API call that creates a resource (`clients().create()`, `getProtocolMappers().createMapper()`, `users().create()`) returns a JAX-RS `Response`. Always call `r.getStatus()` and assert `== 201` before calling `r.close()`. A silent non-201 means the resource was never created, but the test will not fail until runtime. (b) In IT tests, never rely on KC to issue JWTs — use locally-signed RSA JWTs. KC should only be used to test what KC actually does (user/role management operations). Token issuance via KC in tests adds a fragile KC-version-specific dependency that breaks silently. (c) When providing a test `JwtDecoder` via `@TestConfiguration` + `@Import`, always add `@Primary` to the `@Bean` method. `@ConditionalOnMissingBean(JwtDecoder.class)` on Spring Boot's auto-configured decoder has no guaranteed evaluation order relative to `@Import`-ed test beans in Spring Boot 3.5 — without `@Primary`, the wrong decoder may be used and all JWTs will be rejected with 401. (d) Never set `spring.security.oauth2.resourceserver.jwt.issuer-uri` to an empty string `""` to "suppress" auto-configuration — `@ConditionalOnProperty` treats empty string as present and Spring Boot will attempt to create a `SupplierJwtDecoder` regardless.

## ERR-MES-025 — Agent applied known pattern without flagging KC25 breaking-change uncertainty
**Date:** 2026-05-21  **Category:** Agent — Confidence Calibration  **Status:** Promoted 2026-05-22
**Symptom:** Agent applied KC protocol mapper approach (`oidc-usermodel-attribute-mapper`, then `oidc-hardcoded-claim-mapper`) across 9 CI iterations without flagging that KC25's User Profile enforcement was a known niche breaking change with shallow training representation. But training data depth on niche breaking changes (User Profile `unmanagedAttributePolicy`, mapper registration failure modes) was shallow. Agent stated confidence without verifying the specific KC25 behavior. No uncertainty flag was raised to the user before committing the fragile approach.

My training data on this specific change may be shallow. Recommend verifying against the actual container before treating the CI run as the first test." Do not spend CI runs discovering what a 2-minute local smoke test would reveal. (b) When using framework features with version-sensitive ordering guarantees (e.g. `@ConditionalOnMissingBean`, bean registration ordering in Spring Boot test contexts), research the exact Spring Boot version's behavior via documentation or WebSearch BEFORE committing — do not assume the pattern works because it is documented in the general case.

## ERR-MES-026 — LocalPrivilegeCache: lazy-loaded Privilege throws outside Hibernate session
**Date:** 2026-05-21  **Category:** Backend — JPA / Security  **Status:** Promoted 2026-05-22
**Symptom:** All ADMIN-token IT tests returned 5xx (authentication/runtime failure) while VIEWER-token tests returned 403 as expected. Pattern: tests expecting 200/201/204/400/404 all failed; tests expecting 401 (no token) and 403 (VIEWER) all passed.
**Root cause:** `LocalPrivilegeCache.getPrivilegesForRole()` had no `@Transactional`. Spring Data JPA repository methods open and close their own transaction. After `findActiveByRoleId()` returned, the Hibernate session was closed. The stream then called `assignment.getPrivilege().getPrivilegeKey()` — a `@ManyToOne(fetch = FetchType.LAZY)` relation — outside the session, causing `LazyInitializationException`. VIEWER had zero seeded privilege assignments so the stream was empty; no lazy access occurred, no exception, VIEWER correctly got 403.
**Fix applied:** Added `@Transactional(readOnly = true)` to `getPrivilegesForRole()` and added `JOIN FETCH a.privilege` to `findActiveByRoleId()` JPQL query to also eliminate the N+1.
**Rule:** Any method that traverses lazy-loaded JPA relations outside of a repository call must be annotated `@Transactional(readOnly = true)`. A method that returns an empty collection never triggers lazy loading — do not let passing no-data tests give false confidence that lazy loading is safe. When implementing a `PrivilegeCache` backed by JPA, use `JOIN FETCH` in the query so the association is loaded in-band, or ensure the caller holds an open transaction.

## ERR-MES-027 — Hibernate 6.5 implicit join on lazy @ManyToOne.id returns 0 rows
**Date:** 2026-05-22  **Category:** Backend — JPA / Hibernate  **Status:** Promoted 2026-05-22
**Symptom:** After adding `@Transactional(readOnly = true)` and `JOIN FETCH a.privilege` to `LocalPrivilegeCache.getPrivilegesForRole()` (ERR-MES-026 fix), all `@RequiresPrivilege`-gated endpoints still returned 403. `PrivilegeService.getPrivilegeMap()` (which uses `findAllActive()`) returned correct data, confirming V003 seeded the DB correctly. Only `findActiveByRoleId(UUID roleId)` returned empty.
**Root cause:** The JPQL `WHERE a.role.id = :roleId` navigates through the lazy `@ManyToOne role` association to access the `id` field. In Hibernate 6.5 (Spring Boot 3.5) this implicit lazy-association navigation does not optimize to a direct FK column comparison; instead it may generate a join or sub-expression that returns 0 rows even when data exists. `findAllActive()` (no association navigation in WHERE) works correctly, as does `a.role.name` when accessed in memory via `getPrivilegeMap()`.
**Fix applied:** Replaced the two-step lookup (`findByName` + `findActiveByRoleId`) in `LocalPrivilegeCache` with a single new query `findPrivilegeKeysByRoleName` that uses explicit `JOIN a.role r JOIN a.privilege p` and filters by `r.name = :roleName`, projecting String scalars directly. This avoids all implicit navigation and lazy-association joins.
**Rule:** In JPQL WHERE clauses, never navigate through a lazy `@ManyToOne` association to access the target's `id` (e.g. `a.role.id = :roleId`). In Hibernate 6.x this implicit join is unreliable. Instead: (a) use an explicit `JOIN a.role r WHERE r.id = :roleId`, or (b) add a read-only `@Column(name="role_id", insertable=false, updatable=false) UUID roleId` to the source entity and filter on that scalar. Verify by checking that `findAllActive()` (no association navigation) returns data while the parameterised query returns empty — that pattern confirms implicit-join failure, not missing data.

## ERR-MES-028 — @Valid on @RequestBody silently no-ops without spring-boot-starter-validation
**Date:** 2026-05-22  **Category:** Backend — Validation  **Status:** Promoted 2026-05-22
**Symptom:** `registerPrivileges_invalidKeyFormat_returns400()` returned 204 NO_CONTENT instead of 400. The `@Pattern` constraint on `PrivilegeItemRequest.privilegeKey` was never triggered; the service persisted the invalid key and returned success.
**Root cause:** `spring-boot-starter-web` includes `jakarta.validation-api` (the spec) but NOT Hibernate Validator (the implementation). Symptom: validation tests return the success status code instead of 400 — no error is logged. Always add `spring-boot-starter-validation` to any service that uses `@Valid` or `@Validated` on request bodies.

## ERR-MES-029 — Explicit JPQL JOIN on lazy @ManyToOne also returns 0 rows in Hibernate 6.5
**Date:** 2026-05-22  **Category:** Backend — JPA / Hibernate  **Status:** Promoted 2026-05-22
**Symptom:** After ERR-MES-027 fix (`findPrivilegeKeysByRoleName` with explicit `JOIN a.role r JOIN a.privilege p WHERE r.name = :roleName`), all `@RequiresPrivilege`-gated endpoints still returned 403. The new explicit-JOIN query did not return data despite V003 seeding being confirmed correct by `findAllActive()`.
**Root cause:** The Hibernate 6.5 behavior described in ERR-MES-027 (returns 0 rows for parameterised JPQL queries that navigate through lazy `@ManyToOne` associations on `RolePrivilegeAssignment`) applies to BOTH implicit navigation (`a.role.id = :roleId`) AND explicit JPQL joins (`JOIN a.role r WHERE r.name = :roleName`). The common factor is any parameterised WHERE filter that references an associated entity field. `findAllActive()` (no association navigation in WHERE) is unaffected and returns correct data.
**Fix applied:** Replaced `findPrivilegeKeysByRoleName` in `LocalPrivilegeCache.getPrivilegesForRole` with `findAllActive()` + Java stream filter — the same pattern used in `PrivilegeService.getPrivilegeMap()` which is proven to work. Removed the now-dead `findPrivilegeKeysByRoleName` method from `RolePrivilegeRepository`.
**Rule:** In Hibernate 6.5, any JPQL query on an `@Audited` entity that navigates a lazy `@ManyToOne` association in the WHERE clause — whether implicitly (`a.role.id = :id`) or via explicit `JOIN` (`JOIN a.role r WHERE r.name = :name`) — is unreliable and may return 0 rows. For privilege cache lookups, use `findAllActive()` (no association navigation in WHERE) and filter by role name in Java inside a `@Transactional(readOnly = true)` method. This is the only approach verified to work in this Hibernate version.

## ERR-MES-030 — LocalPrivilegeCache lazy loading silently returns empty in Spring Security filter context
**Date:** 2026-05-22  **Category:** Backend — JPA / Security  **Status:** Promoted 2026-05-22
**Symptom:** After ERR-MES-029 fix (using `findAllActive()` + Java stream filter in `LocalPrivilegeCache`), all `@RequiresPrivilege`-gated endpoints still returned 403. `PrivilegeService.getPrivilegeMap()` (also uses `findAllActive()` + lazy load) returned correct data — proving the DB seed and query were correct.
**Root cause:** `LocalPrivilegeCache.getPrivilegesForRole()` runs in the Spring Security filter chain, which executes BEFORE `OpenEntityManagerInViewInterceptor` (OEMIV) binds an EntityManager to the thread. `PrivilegeService.getPrivilegeMap()` runs inside a web request, AFTER OEMIV has already bound an EntityManager, so lazy loading works there. In the security filter context, `@Transactional(readOnly = true)` on `getPrivilegesForRole()` should also create a session — but the lazy loading of `a.getRole().getName()` in the stream processing (after `findAllActive()` returns) fails silently (no exception, returns empty set). The result is an empty privilege set → all `@RequiresPrivilege` checks return 403.
**Fix applied:** Replaced `RolePrivilegeRepository` + JPQL + lazy loading with `JdbcTemplate` + native SQL in `LocalPrivilegeCache`. The native SQL (`SELECT p.privilege_key FROM iam.role_privilege rp JOIN iam.role r ON r.id = rp.role_id JOIN iam.privilege p ON p.id = rp.privilege_id WHERE rp.revoked_at IS NULL AND r.name = ?`) returns scalar strings directly — no entity loading, no lazy associations, no Hibernate/Envers involvement. Single atomic query per call.
**Rule:** `PrivilegeCache.getPrivilegesForRole()` is called from the Spring Security filter chain (before OEMIV, before the transaction interceptor may be reliable in this context). Any implementation that requires lazy loading of JPA associations inside that method will silently return empty results. Use `JdbcTemplate` with native SQL in any `PrivilegeCache` implementation that is backed by a local DB. Do NOT use JPQL + lazy entity traversal in security filter–invoked beans, even with `@Transactional`.

## ERR-MES-031 — Hibernate Envers calls `nextval('revinfo_seq')` without schema prefix
**Date:** 2026-05-22  **Category:** Backend — Hibernate Envers  **Status:** Promoted 2026-05-22
**Symptom:** `grantPrivilege` (PUT `/roles/{id}/privileges/{id}`) returned 500 with `ERROR: relation "revinfo_seq" does not exist`. The grant itself succeeded (DB row saved), but the transaction rolled back at commit because Envers could not generate a revision ID. The test's `put()` helper did not check the response status, so the test proceeded and the GET later returned VIEWER with no privileges.
**Root cause:** `application.yml` set `org.hibernate.envers.default_schema: iam` (Envers-specific) but NOT `hibernate.default_schema: iam` (Hibernate-wide). Envers uses Hibernate's standard `SequenceStyleGenerator` to generate IDs for the `revinfo` table. Without `hibernate.default_schema`, Hibernate produces `SELECT nextval('revinfo_seq')` — no schema prefix. The sequence was created as `iam.revinfo_seq` (V004 migration), so PostgreSQL returns `relation "revinfo_seq" does not exist`.
**Fix applied:** Added `hibernate.default_schema: iam` under `spring.jpa.properties` in `application.yml`. This makes Hibernate qualify all unqualified sequence/table references with `iam.`, so `revinfo_seq` is resolved as `iam.revinfo_seq`.
**Rule:** When all Hibernate entities and Flyway migrations live in a non-public schema, set BOTH `spring.jpa.properties.hibernate.default_schema: <schema>` AND `spring.jpa.properties.org.hibernate.envers.default_schema: <schema>`. The Envers-specific property covers audit table names; the Hibernate property covers sequences (including the Envers revision sequence). Missing `hibernate.default_schema` causes Envers to call `nextval('revinfo_seq')` without a schema prefix, which fails at commit time — not during the main operation, making the error non-obvious.

## ERR-MES-032 — Keycloak 24+ unmanaged attributes DISABLED by default breaks org_id in tests
**Date:** 2026-05-22  **Category:** Testing — Keycloak  **Status:** Promoted 2026-05-22
**Symptom:** 4 `UserControllerIT` tests failed in CI: `listUsers` returned an empty list, and `getUser`/`setUserRoles`/`deactivateUser` returned 404. `createUser_withAdminToken_returns201` passed. Docker was available and the realm was created successfully.
**Root cause:** Keycloak 24+ defaults `unmanagedAttributePolicy` to `DISABLED`. With this policy, custom user attributes not declared in the User Profile schema — including `org_id` — are silently dropped on create and not returned on read, even via the Admin REST API. This caused: (a) `listUsersByOrgId` calling `searchByAttributes("org_id:...")` to return an empty list (attribute not indexed/findable); (b) `findUserById` returning a `UserRepresentation` where `getAttributes()` returns null, causing `verifyOrgOwnership` to throw `UserNotFoundException` (404). Tests that created users and checked the immediate 201 response body passed because the response is built from the non-attribute fields (email, firstName, enabled) — no attribute access happens until a subsequent GET.
**Fix applied:** Added `enableUnmanagedAttributes(Keycloak)` helper to `UserControllerIT.setupKeycloak()` that calls `users().userProfile().getConfiguration()`, sets `UnmanagedAttributePolicy.ENABLED`, and calls `users().userProfile().update(config)`. Also made `createRealm` idempotent.
**Rule:** When creating a Keycloak realm programmatically in tests (KC 24+), always configure the User Profile to allow unmanaged attributes if the code sets custom user attributes (e.g. `org_id`, `tenant_id`) via `user.setAttributes(...)`. Without this, attributes are silently dropped by KC — no error is returned, but reads return null. The symptom is: user creation returns 201 but subsequent lookups by ID return 404 or empty lists. Fix: call `users().userProfile().update(config)` with `UnmanagedAttributePolicy.ENABLED` after realm creation.

## ERR-MES-034 — `jacocoRootReport` fails in Gradle 9.0: missing `jacocoClasspath` and implicit dependency errors
**Date:** 2026-05-22  **Category:** Build — Gradle  **Status:** Promoted 2026-05-22
**Symptom:** CI SonarCloud step failed with: (a) `Task ':jacocoRootReport' uses this output of task ':services:iam-service:jacocoTestReport' without declaring an explicit or implicit dependency` (same for gateway-service and lib-common-security); (b) `Type 'JacocoReport' property 'jacocoClasspath' doesn't have a configured value`.
**Root cause:** Two separate issues: (1) The root `build.gradle` registered `jacocoRootReport` (a `JacocoReport` task) without applying the `jacoco` plugin to the root project. In Gradle 8.x this was only a warning; Gradle 9.0 makes it a build error.
**Fix applied:** (1) Added `apply plugin: 'jacoco'` to the root project (outside `subprojects`). (2) Added `dependsOn sub.tasks.named('jacocoTestReport')` alongside the existing `dependsOn sub.tasks.named('test')` inside the `subprojects.each` block of `jacocoRootReport`.

Without (a), `jacocoClasspath` is not configured. Without (b), Gradle 9.0 rejects `fileTree(rootDir)` as an input with an implicit dependency error.

## ERR-MES-019 — ESLint flat config rejects `processor: angular.processInlineTemplates`
**Date:** 2026-05-20  **Category:** Frontend — ESLint  **Status:** Promoted 2026-05-20
